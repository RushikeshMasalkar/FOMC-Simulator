# Extension reconnaissance and blockers

> **Historical audit:** This document records the earlier sandbox state. The owner now reports a completed Gemini ensemble on Windows; see [Extension results](EXTENSION_RESULTS.md). Those private artifacts were not available for independent verification here.

Audit date: 2026-11-04. At the time of the audit, Phase 1 was **blocked**. The extension has since been implemented and exercised with synthetic data only; no real-data model evaluation or LLM calls have been made. The attached nine-page paper was examined alongside the repository. This document is an audit, not an ablation result.

## Paper and implementation

The paper evaluates 16 scheduled meetings in 2023–2024 with five simulations each and says it uses GPT-4o agents; it reports an average of about 60,464 tokens per chain-of-draft discussion. The paper itself explicitly mentions FedWatch probabilities as inputs. Thus the proposed statement that the original committee ignores market-implied expectations is incorrect: the extension would add a statistical bond-market prior to a committee that is already designed to use market expectations. Overlapping information makes a fitted market weight difficult to interpret as independent new information.

The `base` and `chain_of_draft` versions each implement sequential CrewAI tasks in their respective `src/bny_capstone_crew/crew.py`, with roles in `config/agents.yaml`. The economist proposes policy options; three clustered member agents (regional, academic, central, the latter including the Chair) analyze, discuss, and cast separate final votes; an analyst writes a statement and consolidates the votes. There is no separate explicit final Chair or hard committee-decision task. A majority of the three signed rate changes is a plausible *new* aggregation rule but is not the repository's existing evaluation; ties, ambiguous values, and disagreement between statement and votes would need an explicit policy.

`base/src/bny_capstone_crew/crew.py` hard-codes meeting code `22_6`; it loads meeting-specific Beige Book, current macro and dot-plot PDFs and a historical macro CSV via CrewAI knowledge sources. The economist uses `gpt-4o`; the other agents use `openai/gpt-4o-mini` at temperature 0.03; a `gpt-4o` manager configuration exists but is not used by this sequential crew. Additional OpenRouter/Anthropic LLM objects are instantiated using environment variables, even though not used in this crew. Memory is enabled and long-term memory comes from `memory/fomc_longterm.db`. The code specifically asks the analyst and economist to use FedWatch probabilities, and forbids options with zero implied probability. These instructions mean the replication is not market-blind.

`chain_of_draft` adds Chain of Draft, uses `gemini/gemini-3.1-flash-lite` at 0.03 for its agents in the checked-out code, and requires `GEMINI_API_KEY` and a local Ollama `nomic-embed-text` embedding service. This differs from both the base code and the paper; the model associated with prior aggregate `results.txt` entries is not established by these files. It initializes only a meeting-specific dot-plot PDF and filtered historical CSV even though tasks request a current-macro PDF, Beige Book and FedWatch; those sources are not wired into that version's current knowledge loader. Its `main.py` schedules four meeting codes, two runs each; the date passed as input does not repair the three hard-coded `September 18, 2024` vote prompts in `crew.py`. Some filtered knowledge files exist for these four meetings, but many other meeting codes lack them. Such issues must be resolved and provenance checked before generating valid backtests; silently changing prompts or models would not reproduce the baseline.

## Meetings, labels, outputs and evaluation

`state_of_art_model/fomc_meetings.csv` provides `Date` and `Outcome` (`CUT`, `NO CHANGE`, `HIKE`) for 255 rows, 1994–2025. The extension's requested mapping is 0 = CUT, 1 = NO CHANGE/hold, 2 = HIKE. `base/Automated_metrics.py` also contains explicit `code2fomcdate` and `code2vote` dictionaries for a selected set of meetings. Before using either source for results, reconcile dates and outcomes where they overlap; they are not a substitute for matched committee outputs.

The chain-of-draft crew saves per-run logs as `chain_of_draft/results/{meeting_code}_run{run_number}/fomc_simulation.md` and analyst output as `rate_summary.json`. Eight checked-in JSON summaries cover **only four dates**: 2023-02-01, 2023-05-03, 2024-03-20 and 2024-09-18, two runs each. `24_9_run1` has `4.62%` in the `vote` fields, apparently a rate level rather than the requested signed change; treating it as a hike would be wrong. The corresponding statement says a 25 bp cut, but it would require a validated explicit parsing/reconciliation protocol. All other checked-in votes are signed changes. Files are not a validated complete set of paper results.

`base/run_crew.sh` runs five simulations, renames outputs and resets memory. `base/Automated_metrics.py` and the chain-of-draft counterpart glob JSON summaries, compare **individual** vote strings with `code2vote`, report agreement and vote accuracy, and compute statement similarity to a fetched FOMC statement. Aggregate logs in `base/results.txt` and `chain_of_draft/results.txt` do not supply reliable per-meeting, per-run hard decisions and cannot be used as a replacement for missing summaries. The state-of-the-art CSV predictions belong to a different statistical baseline, not the committee.

## Separation and pre-spend estimate

The three member `*_vote` tasks have the three discussion tasks as explicit context, and detailed logs include completed task outputs. In principle the discussions could be frozen and the **three** member votes replayed at temperature 0.7, followed by deterministic parsing and a documented majority rule. That is a candidate for the preferred cached-deliberation strategy, not a verified callable isolation: the baseline has no such API, task context and agent knowledge/memory behavior must be reproduced and tested, and discussions already contain preliminary votes. Re-running the analyst summary alone would merely reformat frozen votes, not sample a committee decision. If a faithful vote replay cannot be validated, use full runs instead and disclose the change.

For the 14-task chain-of-draft workflow, idealized lower bounds for `M` meetings and `K` samples are `M × (8 + 3K)` calls from scratch for frozen deliberation plus three vote tasks per sample (or `3MK` if valid deliberations are already cached), versus `14MK` for full runs. At K=7: per meeting 29 versus 98; four meetings 116 versus 392; a three-meeting smoke test 87 versus 294. These are only task-level lower bounds: a CrewAI task can require multiple LLM calls, tool iterations, embedding calls, retries and summarization, so they are not enforceable upper bounds. The paper's 60,464 average total tokens per full discussion suggests roughly 1.69 million tokens for 28 full runs at four meetings, but neither prompt/completion split nor provider/model price is established, so a defensible dollar estimate is unavailable. Actual guard must count **provider requests including retries**, stop before exceeding an explicitly configured maximum, and include all models; task-count estimates alone do not constitute a hard budget. The later implementation counts API requests, including retries, with a per-invocation guard; it uses existing transcripts only and does not run the full crew.

## Integrity risks and stop condition

- All three chain-of-draft vote task prompts explicitly say September 18, 2024, regardless of the meeting. The code asks for exact dates; knowledge sources include meeting dates, target changes and indicators identifying time periods; member identity and Chair-related information can reveal historical context. Historical outcomes can be memorized by the model. Dot plots, prior meeting statements and market inputs need release-time and content audits; meeting date alone is not a point-in-time availability guarantee. The historical filtered CSVs remove current/future meeting rows for the four checked-in dates, but that does not prove the PDFs or other data are leakage-free.
- The provider's knowledge cutoff for the exact checked-in Gemini model is not established here; no defensible pre/post-cutoff split or anonymization experiment has been performed.
- Direct FRED CSV download of `DFF` was attempted and failed with an SSL connection error. This sandbox's permitted outbound hosts do not include FRED. No local `data/fred/` cache exists; `pandas_datareader` would require access to the same blocked service and would not fix the restriction. The checked-in quarterly predictor table and meeting-level macro CSVs lack the required complete daily series and point-in-time feature timestamps and cannot replace the requested dataset without changing the design.
- Even with market data, only four dated committee outputs across two calendar years exist. With fusion trained strictly on **earlier out-of-sample committee/market pairs**, the first output year cannot train fusion and the next has at most two prior meetings; no five-year / 40-meeting initial committee history exists. A statistically meaningful nested walk-forward table across all six variants cannot be recovered from these artifacts. The user-specified instruction says to stop if a phase is blocked; no synthetic outputs or in-sample substitutions were used.

## Proposed path to unblock

1. Provide a permitted route to FRED, or provide dated CSV extracts for DFF, DTB3, DTB6, DGS1, DGS2, DGS10 and VIXCLS (covering at least the training window and test years, with provenance). Validate revisions/publication timing and the two-day cutoff.
2. Provide the full per-meeting baseline outputs and their exact model/configuration, including earlier years for fusion training, or explicitly approve a new, budgeted committee-generation campaign. Parameterize and verify meeting-specific prompts and point-in-time knowledge first; document any departure from the original. Establish a deterministic validated committee-decision rule and handle invalid vote formats without inventing labels.
3. Set an explicit maximum provider request budget and obtain approved provider connectivity/credentials outside chat. Run a guarded 3–5 meeting smoke test and inspect outputs before authorizing the full batch. Only then fit nested walk-forward models and report actual uncertainty and failures.
